## Scope and schema

| Table | Columns |
| --- | --- |
| `crm_leads` | `id`, `user_id`, `source`, `source_url`, `name`, `email`, `phone`, `whatsapp`, `notes`, `status`, `qualification_score`, `created_at`, `updated_at` |
| `crm_contacts` | `id`, `user_id`, `name`, `email`, `phone`, `whatsapp`, `company_name`, `job_title`, `contact_type`, `lifecycle_stage`, `opted_in_email`, `opted_in_whatsapp`, `opted_in_sms`, `created_at`, `updated_at` |

Both owners default to `auth.uid()` and reference `auth.users(id)` with account-deletion cascade. UUID IDs and timestamps are generated by PostgreSQL. Source/status/length constraints and owner-specific case-insensitive unique email indexes apply. Consent defaults **false**, never inferred from entering contact information.

RLS permits own-row SELECT/INSERT only for existing trusted `profiles.role` PROFESSIONAL or ADMIN. ADMIN gets no cross-user exception. Revoke all table grants from PUBLIC, anon and authenticated, then grant authenticated SELECT plus column INSERT:

- Leads: `source, source_url, name, email, phone, whatsapp, notes`.
- Contacts: `name, email, phone, whatsapp, company_name, job_title`.

Clients cannot insert owner/status/score/consent/timestamps. No UPDATE, DELETE, TRUNCATE grants or policies. APIs read the verified server user and trusted profile role; strict body schemas reject owner or protected field overrides. Status changes, qualification scoring and communication consent are outside this slice.

Dashboard counts only real lead rows, including source and current UTC-month metrics. Missing conversations/tasks/pipeline are `null` and shown as “En preparación”; never fabricated zeros. Manual creation is `/crm/leads/new`, reachable from the existing prospect list. No external messages, campaigns or OAuth activation.

## Rollback and data effects

The migration creates two tables/indexes/policies; it changes no existing tables or user permissions on existing tables, sends nothing and provisions no accounts. Applying it is a persistent live schema/grant change requiring approval. Once capture begins, rows contain personal contact data; deleting the owner account would cascade-delete its CRM rows through the declared FK.

For a reversible stop, roll application code back and revoke access using the reviewed `supabase/rollback/crm_manual_capture_disable.sql` only after approval. It explicitly revokes column INSERT grants too and **keeps all data**. Verify denial afterward; do not drop tables or edit migration history. Restoring access requires re-reviewing exact grants. Dropping tables after data exists is irreversible without a verified backup/export and separate explicit approval; no destructive rollback is provided or executed here.
